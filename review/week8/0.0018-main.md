# Code Review: 0.0018/main.go

**Rating: 2/10**

## Overview

Docker client code that lists and stops all running containers. Uses the deprecated Moby client package and has hardcoded configuration with no error context.

## What This Code Does

Lists all Docker containers and stops each one immediately with zero timeout. 35 lines attempting container management with minimal error handling.

## Issues

### Critical

1. **Wrong import path** - Uses `github.com/moby/moby/client` which is deprecated. Should use `github.com/docker/docker/client`
2. **Wrong API types** - `client.ContainerListOptions{}` and `containers.Items` don't exist in the actual API. Should be `container.ListOptions{}` and range directly over `containers`
3. **Code doesn't compile** - This will fail at build time with "undefined: client.ContainerListOptions" and "containers.Items undefined"

### Major

1. **Dangerous operation with no confirmation** - Stops ALL containers with zero timeout. No warning, no filter, no confirmation
2. **Zero error context** - All errors just `panic(err)` with no message about what failed
3. **No timeout on context** - `context.Background()` with no deadline means operations could hang indefinitely
4. **Hardcoded timeout value** - `noWaitTimeout := 0` with comment explaining it, but no way to override
5. **Silent failure on stop** - If container stop fails, panics without saying which container

### Minor

1. **Inconsistent error handling** - Uses `log.Fatal` pattern elsewhere but `panic()` here
2. **No logging before destructive operation** - Only prints after stopping each container
3. **Truncated container ID** - `container.ID[:10]` will panic if ID is shorter than 10 characters
4. **Comment placement** - Inline comment for `noWaitTimeout` breaks flow

## What You Learned

Attempted to use Docker Go client for the first time. Shows understanding that:

- Docker operations need a client connection
- Contexts are required for Docker API calls
- Resources should be closed with defer
- Container stop operations can have timeouts

Did not learn:

- How to find correct import paths (deprecated package used)
- How to verify API structure before writing code
- That untested code might not compile

## Testing

No tests. No manual testing verified (code doesn't compile). No check if Docker daemon is running.

## Final Verdict

**This code does not work.** Uses wrong import path and wrong API types. Will fail to compile with "undefined" errors. Even if imports were fixed, stopping all containers with zero notice is dangerous. The pattern of "list things and destroy them immediately" needs safety checks.

Week 8 Challenge recommendation: Before committing code, run `go build` to verify it compiles. Check documentation for correct API usage. Add at least one safety check before destructive operations.
