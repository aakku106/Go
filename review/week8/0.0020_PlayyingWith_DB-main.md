# Code Review: 0.0020_PlayyingWith_DB/main.go

**Rating: 5.5/10**

## Overview

PostgreSQL database operations: create table, insert user, display all users. First database integration attempt with proper connection handling and defer patterns. Hardcoded credentials with no environment variable support.

## What This Code Does

Connects to local PostgreSQL, creates users table if not exists, inserts one user, retrieves and logs all users. 90 lines with struct and helper functions.

## Strengths

1. **Proper resource cleanup** - `defer db.Close()` and `defer rows.Close()` used correctly
2. **Connection verification** - Uses `db.Ping()` to verify connection before proceeding
3. **SQL injection prevention** - Uses parameterized queries `$1, $2` not string concatenation
4. **RETURNING clause** - `INSERT...RETURNING id` to get primary key is correct PostgreSQL
5. **IF NOT EXISTS** - CREATE TABLE won't fail if table already exists
6. **Structured data** - Users struct for type safety
7. **Error handling** - Checks errors after each database operation
8. **Logging** - Uses log package consistently for output

## Issues

### Critical

1. **Hardcoded credentials** - Password "aakku106" in connection string (line 12). Should use environment variables
2. **log.Fatal in library function** - createTable, InsertIntoUserTable, DisplayAllUserInfo use log.Fatal which calls os.Exit(1). Library functions should return errors, not exit program
3. **Incorrect error handling in createTable** - Lines 26-30 try to recover from panic, but line 40 uses log.Fatal which calls os.Exit - defer won't catch this

### Major

1. **Typo: queue** - Line 61, variable named `queue` should be `query`
2. **Typo: "handeling"** - Comment at top of panic.go says "handeling", should be "handling"
3. **Typo: "nehavior"** - File path comment, should be "behavior"
4. **Folder name typo** - "PlayyingWith_DB" has extra 'y', should be "PlayingWith_DB"
5. **Grammar: "beth opean"** - Should be "both open" (file comment)
6. **Comment lie** - Line 28 says defer recover won't work with log.Fatal but doesn't explain why (os.Exit bypasses defers)
7. **Commented variables** - Line 68 has `// data := []Users{}` - dead code
8. **Inconsistent patterns** - InsertIntoUserTable returns int, others return nothing. Should all return (int, error) or similar

### Minor

1. **No connection pooling config** - Uses default pool settings
2. **Migration comment** - Line 24 says "use migrations" but doesn't show how
3. **Manual struct scanning** - Line 70 declares id, name, address separately. Could use Users struct
4. **No limit on SELECT** - DisplayAllUserInfo does `SELECT * FROM users` with no LIMIT - could be dangerous with large tables
5. **Magic numbers** - Hardcoded VARCHAR(20), VARCHAR(50) with no constants
6. **Type inconsistency** - Users.Name is string but DB is VARCHAR(20) - no validation length matches
7. **Package comment missing** - No explanation what 0.0020_PlayyingWith_DB does
8. **CREATE TABLE in main** - Should be separate migration, not run on every startup
9. **Variable scope** - Lines 19-21 declare users in main but could be inline where used

## What You Learned

- PostgreSQL library usage (github.com/lib/pq)
- Blank import for driver registration `_ "github.com/lib/pq"`
- Connection string format for PostgreSQL
- db.Ping() to verify connection
- Parameterized queries ($1, $2) prevent SQL injection
- RETURNING clause in INSERT statements
- rows.Next() pattern for iteration
- defer rows.Close() for cursor cleanup
- SERIAL PRIMARY KEY for auto-increment

Did not learn:

- Environment variables for credentials
- Migration tools (mentioned but not used)
- Returning errors from functions vs log.Fatal
- When to use panic/recover vs normal errors

## Testing

No tests. Database code should have tests using testcontainers or mocked DB.

## Final Verdict

**First database integration with correct SQL patterns but critical credential/error handling issues.** The SQL is well-written: parameterized queries, IF NOT EXISTS, RETURNING clause, proper row iteration. Database connection handling with defer is correct.

**Critical flaws:**

1. Hardcoded password in source code
2. log.Fatal in library functions (should return errors)
3. Misunderstanding of recover() vs os.Exit
4. Variable named `queue` instead of `query`

The recover defer in createTable (lines 26-30) won't work because log.Fatal calls os.Exit which bypasses all defers. Comment acknowledges this but doesn't fix it - should return error instead.

For Week 8 final week, first database work is ambitious. The SQL knowledge is solid but Go error handling patterns still shaky. Using log.Fatal in library functions is antipattern - only main() should decide to exit program.
