**3. Struct Doesn't Match API Response**

```go
type Location struct {
 Country  string `json:"country"`
 Province string `json:"province"`
 City     string `json:"city"`
 Tole     string `json:"tole"`
}

type Address struct {
 Email     string `json:"email"`
 *Location `json:"location"`
}

type User struct {
 Id       uint   `json:"id"`
 Name     string `json:"name"`
 Age      uint8  `json:"age"`
 *Address `json:"address"`
}
```

But jsonplaceholder.typicode.com/users returns:

```json
{
  "id": 1,
  "name": "Leanne Graham",
  "username": "Bret",
  "email": "Sincere@april.biz",
  "address": {
    "street": "Kulas Light",
    "suite": "Apt. 556",
    "city": "Gwenborough",
    "zipcode": "92998-3874",
    "geo": {
      "lat": "-37.3159",
      "lng": "81.1496"
    }
  },
  "phone": "1-770-736-8031 x56442",
  "website": "hildegard.org",
  "company": { ... }
}
```

Your struct expects:

- `age` (doesn't exist in API)
- `location` with country/province/city/tole (API has street/suite/city/zipcode/geo)
- `email` nested under address (API has email at top level)

**Result**: Unmarshal partially succeeds but most fields are empty because structure mismatch.

Comment admits this (lines 74-91) but then says "thats why we get only 2 readable value" - actually you get:

- id (matches)
- name (matches)
- username (ignored, not in struct)
- email (ignored, your Address.Email expects nested location)
- age (always 0, API doesn't send it)
- address (ignored, structure doesn't match)

This demonstrates a real problem but incorrectly. Should either:

**Option A**: Match actual API structure

```go
type Geo struct {
 Lat string `json:"lat"`
 Lng string `json:"lng"`
}

type Address struct {
 Street  string `json:"street"`
 Suite   string `json:"suite"`
 City    string `json:"city"`
 Zipcode string `json:"zipcode"`
 Geo     Geo    `json:"geo"`
}

type User struct {
 Id       uint    `json:"id"`
 Name     string  `json:"name"`
 Username string  `json:"username"`
 Email    string  `json:"email"`
 Address  Address `json:"address"`
 Phone    string  `json:"phone"`
 Website  string  `json:"website"`
}
```

**Option B**: Use different API that matches your struct

Find API that returns user data with age/country/province or create mock endpoint.

```

Comment says "address of some slice" but response.Body is `io.ReadCloser` interface. The output `&{[] {0x14000204000} <nil> <nil>}` is the default fmt.Println of the internal buffer struct, not a slice address.

// To read the actual JSON data, use io.ReadAll
```

**6. Inconsistent Pointer Usage**

```go
type Address struct {
 Email     string `json:"email"`
 *Location `json:"location"`  // Embedded pointer
}

type User struct {
 Id       uint   `json:"id"`
 Name     string `json:"name"`
 Age      uint8  `json:"age"`
 *Address `json:"address"`  // Embedded pointer
}
```

Why pointers? For optional fields, this makes sense. But Email is not a pointer while Location and Address are. Inconsistent design.

If these are optional (can be null in JSON):

```go
type Address struct {
 Email    *string   `json:"email,omitempty"`
 Location *Location `json:"location,omitempty"`
}

type User struct {
 Id      uint     `json:"id"`
 Name    string   `json:"name"`
 Age     *uint8   `json:"age,omitempty"`  // Optional field
 Address *Address `json:"address,omitempty"`
}
```

If they're required, don't use pointers:

```go
type Address struct {
 Email    string   `json:"email"`
 Location Location `json:"location"`
}

type User struct {
 Id      uint    `json:"id"`
 Name    string  `json:"name"`
 Age     uint8   `json:"age"`
 Address Address `json:"address"`
}
```

Current mix of pointer and non-pointer is unclear.
