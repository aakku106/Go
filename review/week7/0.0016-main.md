## Overview

Simple 2D game using Ebiten library. Creates window with black background and red circle controlled by WASD keys. Player character has embedded Position struct with pointer, Enemy struct declared but never used. Global variable for player instance.

---

## Strengths

1. **Working Code** - Game runs and responds to input
2. **Clean Methods** - Game struct implements Ebiten interface (Update, Draw, Layout)
3. **Constructor Pattern** - NewPlayer creates properly initialized player
4. **Embedded Pointer** - Player embeds \*Position (correct pointer embedding)
5. **Library Usage** - Uses vector.DrawFilledCircle correctly

## Issues

### Critical

**1. Wrong Library Imported**

```go
import (
 "github.com/hajimehoshi/ebiten/v2"
 "github.com/hajimehoshi/ebiten/v2/vector"
 "image/color"
 "log"
)
```

File name says `0.0016` but code shows two different game libraries mixed. Comments in git history mention "Raylib" but code uses Ebiten. This is not Raylib code at all.

**Git commit**: "Add game module and movement functions for player control"  
**Actual code**: Uses github.com/hajimehoshi/ebiten/v2 (NOT Raylib)

Either folder name is wrong or you switched libraries mid-development.

**2. Global Variable**

```go
var aakku = NewPlayer()
```

Global mutable state. Problems:

- Cannot have multiple players
- Cannot test Update() in isolation
- Tight coupling between Game and player instance
- Name "aakku" is not descriptive

**Should be**:

```go
type Game struct{
 player *Player
}

func NewGame() *Game {
 return &Game{
  player: NewPlayer(),
 }
}

func (g *Game) Update() error {
 if ebiten.IsKeyPressed(ebiten.KeyW) {
  g.player.MoveUp()
 }
 // ...
}
```

**3. Unused Enemy Struct**

```go
type Enemy struct {
 *Position
}
```

Declared but never instantiated, never used. Dead code. Delete it or implement enemy functionality.

**4. Zero Error Handling**

```go
func (g *Game) Update() error {
 // ...
 return nil
}
```

Update always returns nil. If movement methods had errors (boundary checks, collision detection), they're ignored.

### Major

**1. Position Initialized to Zero**

```go
func NewPlayer() *Player {
 return &Player{
  Position: &Position{},
 }
}
```

Creates Position{x: 0, y: 0}. Player starts at top-left corner (0,0) which is likely off-screen or awkward starting position.

**Should be**:

```go
func NewPlayer() *Player {
 return &Player{
  Position: &Position{
   x: 320,  // Center of 640x480 window
   y: 240,
  },
 }
}
```

**2. Magic Numbers**

```go
vector.DrawFilledCircle(screen, float32(aakku.Position.x), float32(aakku.Position.y), 20, color.RGBA{255, 0, 0, 255}, false)
```

Hard-coded values:

- `20` - player radius
- `255, 0, 0, 255` - red color
- `640, 480` - window size

**Should be constants**:

```go
const (
 WindowWidth  = 640
 WindowHeight = 480
 PlayerRadius = 20
)

var PlayerColor = color.RGBA{255, 0, 0, 255}
```

**3. Inconsistent Casing**

```go
func (g *Game) Update() error {  // Lowercase method names (correct for interface)
```

But:

```go
type Game struct{}  // Empty struct (no data)
```

Game struct has no fields but uses receiver. Should store player:

```go
type Game struct {
 player *Player
}
```

**4. No Boundary Checking**

Player can move infinitely in any direction. No check against window bounds (640x480). Player will eventually move off-screen and disappear.

Movement methods in movments.go add/subtract without bounds:

```go
func (p *Position) MoveRight() {
 p.x += 2  // No upper bound check
}
```

Should clamp to window size.

**5. Unnecessary Type Conversions**

```go
vector.DrawFilledCircle(screen, float32(aakku.Position.x), float32(aakku.Position.y), 20, ...)
```

Position.x and Position.y are float64, converted to float32 every frame. If DrawFilledCircle requires float32, Position should use float32 to begin with:

```go
type Position struct {
 x float32
 y float32
}
```

Avoids conversion on every draw call.

### Minor

**1. Comment Quality**

```go
func (g *Game) Layout(outsideWidth, outsideHeight int) (int, int) {
 // Size of the logical screen.
 return 640, 480
}
```

Comment doesn't explain why logical size is fixed while outside size varies. Should explain:

```go
// Layout returns the logical screen size.
// Ebiten scales this to match actual window dimensions.
// Fixed at 640x480 for consistent game logic regardless of window size.
```

**2. Incomplete Features**

File has Position/Player/Enemy structs but no game loop logic:

- No scoring
- No enemy spawning
- No collision detection
- No game over condition

Just a red circle moving on black screen. Not really a game yet.

**3. Method Organization**

Draw method does two things:

```go
func (g *Game) Draw(screen *ebiten.Image) {
 screen.Fill(color.RGBA{0, 0, 0, 255}) // clear screen to black
 // Draw player as a filled circle
 vector.DrawFilledCircle(...)
}
```

Should separate clearing and drawing:

```go
func (g *Game) Draw(screen *ebiten.Image) {
 g.clearScreen(screen)
 g.drawPlayer(screen)
}

func (g *Game) clearScreen(screen *ebiten.Image) {
 screen.Fill(color.RGBA{0, 0, 0, 255})
}

func (g *Game) drawPlayer(screen *ebiten.Image) {
 vector.DrawFilledCircle(screen, ...)
}
```

**4. Embedded Pointer Confusion**

```go
type Player struct {
 *Position
}
```

This works but creates confusion. When you call `aakku.MoveUp()`, it's actually calling `aakku.Position.MoveUp()` through promotion. Direct field would be clearer:

```go
type Player struct {
 pos *Position
}

func (p *Player) MoveUp() {
 p.pos.MoveUp()
}
```

Makes ownership explicit.

## Final Verdict

**3/10** - Working proof of concept but poorly structured. Global variable, unused code, wrong library name, zero error handling, magic numbers throughout. This is prototype quality - functional but not maintainable. Needs boundary checks, proper state management, removal of dead code, and test coverage before it's production-ready.

**Main problems**: Global state, library confusion (Raylib vs Ebiten), unused Enemy struct, no bounds checking.

**What works**: Basic game loop, input handling, drawing.

**Recommended fixes**:

1. Move player into Game struct
2. Delete unused Enemy or implement enemies
3. Add boundary checking in movement
4. Clarify which library you're actually using
5. Add constants for magic numbers
6. Write tests for player creation and movement
